# HEART RELAY（仮）｜初期プロトタイプ前提条件（職員・検証端末）｜2026-11-02

> 出典: Google Docs（2026-11-02 取得、参照用に転記）。現時点の構想、正式仕様ではない。

## 1. 対象範囲
デイサービス1事業所、架空の職員20名の小規模モデル。複数事業所・法人全体は対象外。

## 2. 架空の職員構成（20名）
事業所長1 / 理学療法士2 / 看護師2 / 生活相談員1 / 運転手2 / 介護職員12。
兼務・保有資格・当日の担当業務は基本職種と分けて設計。

## 3. 自宅の検証端末（5台）
Windows PC 1 / iPad mini 5 1 / Androidスマートフォン 3。

## 4. 端末ごとの想定用途（案）
- Windows PC: 入力・集約、分類と伝達先確認のWebアプリ操作
- iPad mini 5: フロア全体の共有タブレット（デジタルホワイトボード）。表示内容・権限は未確定
- Android 3台: 異なる架空職員アカウントで個別通知を検証。音声・書類写真の送信入力端末としても検証

## 5. 開発・検証上の前提
すべて架空データ。実在個人情報を外部AIに入力しない。

## 6. 最小モデルの情報処理フロー（案）
① 取り込み: PCで会議記録・ケアマネ/家族からの連絡・欠席予定・食事形態変更（普通食→おかゆ）等を入力
② AI整理: Claude API等で対象者・用件・重要度・必要な対応・伝達候補先を抽出・分類
③ 人を基準にした振り分け: 職種・資格・兼務・勤務形態・当日担当業務を考慮し、必要な職員を選ぶ。全員一斉配信ではない
④ 端末表示: 選ばれた職員アカウントのAndroidに表示。全体共有情報はiPad共有表示も候補
⑤ 検証: 「必要な人に届く」「不要な人に過度に届かない」「重要内容が欠落しない」「確認ボタンで確認記録が残る」

## 7. 設計時に区別すること
- 宛先は「端末」ではなく「職員本人（アカウント）」。個人向け情報とフロア共通情報は分ける
- 職員モデル20名と実機Android3台は別概念。アカウント割当は今後決める
- 固定属性（職種・資格）と変動属性（当日の勤務・担当業務）を分ける
- 「確認しました」ボタンとアカウント別確認記録は**基本要件**

## 8. 端末からサーバーへの送信（双方向）
音声録音アップロード→文字起こし→AI整理、書類写真→OCR→AI分類→通知。送信元アカウント・日時・資料種類を記録。元データと結果を紐づけ。重要要件だが実装範囲は未確定。

## 9. 個人通知の確認記録（基本要件）
- 個人向け通知に「確認しました」ボタン
- 押下時にサーバーへ 通知ID / 職員アカウントID / 確認日時 を記録
- 配信と確認は別事象。「未確認」「確認済み」を区別し未確認職員が分かる
- 管理側が対象者ごとの確認状況を把握。一覧・再通知仕様は未決定
- 「閲覧」と「明示的な確認」を混同しない。確定要件は後者
- 「確認済み」は理解や対応完了を保証しない
