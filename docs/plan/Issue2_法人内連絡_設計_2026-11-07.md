# Issue #2 法人内複数事業所連携 設計記録（2026-11-07）

[オーナー決定] UI 刷新完了後に Issue #2（人間主導の事業所間情報伝達）に着手。受入れ基準は Issue 本文のとおり。
[Fable 提案] 以下の最小設計で受入れ基準 7 項目を満たす。既存の単一事業所フロー（PC→Claude→Android→確認→PC）と Android アプリは無変更で動くこと。

## 1. データモデル（スキーマ v3、起動時に自動移行）
| テーブル | 追加・新設 | 既定値（移行時） |
|---|---|---|
| `offices`（新設） | `id, name, kind, created_at` | 架空 3 事業所を投入: `A` デイサービス ひだまり（kind=デイサービス）, `B` 老健 やすらぎ（老健）, `C` ひだまり病院（病院） |
| `staff` | `office_id TEXT NOT NULL DEFAULT 'A'` | 既存 20 名は A。B・C に架空職員を 3 名ずつ追加（例: B 相談員・看護師・介護、C 地域連携室・看護師・医事） |
| `messages` | `office_id TEXT NOT NULL DEFAULT 'A'` | 既存は A |
| `board_posts` | `office_id TEXT NOT NULL DEFAULT 'A'` | 既存は A |
| `office_messages`（新設） | `id, from_office_id, to_office_id, source_message_id (null可), title, body, created_by, created_at, acknowledged_at, acknowledged_by` | — |
| `meta.schema_version` | 3 | |
利用者台帳（residents）は A のみ（Issue の対象外「台帳の無条件同期」はしない）。

## 2. API（v3 追加。既存エンドポイントは `office` 省略時 A として後方互換）
| Method | Path | 内容 |
|---|---|---|
| GET | `/api/offices` | `[{id, name, kind}]` |
| GET | `/api/staff?office=A` | 事業所で絞る（省略時 A → Android 無変更） |
| GET | `/api/messages?office=A` | 事業所で絞る（省略時 A） |
| POST | `/api/messages` | body に `office_id`（省略時 A）。照合・解析・配信は**その事業所の職員名簿**のみを使う |
| GET | `/api/board?office=A` | 事業所で絞る（省略時 A）。`board.html?office=B` で切替 |
| GET | `/api/stats?office=A` | 事業所で絞る |
| GET | `/api/office-messages?office=A` | `{inbox: OfficeMessage[], outbox: OfficeMessage[]}`（受信＝to が A、送信＝from が A、新しい順） |
| POST | `/api/office-messages` | `{from_office_id, to_office_id, title, body, created_by, source_message_id?}` → `OfficeMessage`。**人間の明示操作でのみ呼ぶ**。from=to は 400。存在しない事業所は 400 |
| POST | `/api/office-messages/:id/ack` | `{staff_name}` → 受信側の確認を記録（冪等） |
```ts
interface Office { id: string; name: string; kind: string }
interface OfficeMessage { id; from_office: Office; to_office: Office; source_message_id: string|null; title; body; created_by; created_at; acknowledged_at: string|null; acknowledged_by: string|null }
```
制約: `office_messages` の作成経路は上記 POST のみ。解析・配信（`/send`）・ボードからは絶対に作らない（AI による自動送信をコードレベルで不可能にする）。

## 3. 画面
- ヘッダの事業所表示をセレクトに変更（`/api/offices`、localStorage `hr.office`、既定 A）。切替で職員 select・ホーム・配信管理・共有ボードリンク（`board.html?office=X`）が切り替わる。testid `office-select`。
- ナビに「法人内連絡」を追加（`#/corp`）。testid `nav-corp`／スマホ下部タブは「ボード」の隣に「法人内」。
- `#/corp` 画面:
  - 上部「他の事業所へ連絡する」: 送信先事業所（自事業所以外）select `corp-to`、内容の元（「新規入力」または「既存の連絡から選ぶ」= 自事業所の配信済み連絡一覧 select `corp-source`、選ぶと **要約＋必要な対応** を本文に転記、自由に編集可。利用者の個人情報は本文に入れるかを人が判断するため、初期転記は要約と対応のみとし、宛先職員名・除外理由は転記しない）、件名 `corp-title`、本文 `corp-body`、送信前の確認ダイアログ（送信先・件名を再表示）→ `corp-send`。送信後はトーストと送信履歴へ。
  - 下部 2 列: 「受信」(`corp-inbox`、未確認は橙バッジ、「確認しました」ボタン `corp-ack`、確認者＝ヘッダの操作者) と「送信履歴」(`corp-outbox`、相手の確認状況 確認済 hh:mm／未確認)。
- ホーム・配信管理・ボードは自事業所の情報だけを表示（他事業所の `messages`/`board_posts` は混入しない）。
- AI による文面整理は本段階では実装しない（Issue では「補助できる」であり受入れ基準外。[Fable 提案] 時間との兼ね合いで後回し）。

## 4. テスト
- backend: 移行（v2 DB → v3、既存行の office_id=A）、offices 3 件、staff の絞り込み、office-messages の作成・ack・from=to 400・不正事業所 400、`/send` が office_messages を作らないこと、B のボード/メッセージが A の一覧に出ないこと。
- E2E（mock-server も v3 契約へ）: A で通常フロー（既存シナリオ無変更）→ `#/corp` で B へ送信（既存連絡から選択→編集→確認ダイアログ→送信）→ 事業所セレクトで B に切替 → 受信に表示 → 確認 → A に戻ると送信履歴が確認済 → B の配信管理・ボードに A の連絡が無いこと。
- 実機: ユーザーPC で A→B 送信と B での確認、Android（A の職員）が従来どおり受信・確認できること。
