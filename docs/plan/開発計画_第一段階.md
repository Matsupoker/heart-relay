# HEART RELAY（仮）第一段階 開発計画

作成: 2026-11-02（Built with Claude: Japan 2026 開発初日）
正典: `README.md` と `docs/reference/` の4資料（Google Docsから転記）。

## 1. 目的と本質的な課題

- 課題は「情報がないこと」ではなく「存在する情報が必要な職員に届かないこと」。
- 全員一斉送信ではなく、**誰に関係し、何をすべきか**を選別して届け、**本人が確認した事実**を記録する。
- 第一段階は「入力 → AI解析・分類 → 必要な職員への個別伝達 → 確認記録 → PC側への反映」が一連で動くことを実証する。

## 2. 第一段階で実装する機能（MVP）

| # | 機能 | 備考 |
|---|---|---|
| 1 | PC Webアプリ: 連絡事項のテキスト入力 | ブラウザ（Chrome/Edge） |
| 2 | バックエンド: Claude APIで解析（分類・要約・緊急度・対象者・伝達候補・受信者別の本文生成） | AI呼び出し口を抽象化 |
| 3 | PC Webアプリ: AI提案（宛先と個別本文）の確認・修正・**送信承認** | 無条件の自動配信にしない |
| 4 | バックエンド: 職員ごとの配信レコード作成・保存 | SQLite |
| 5 | Androidアプリ: 職員アカウント選択、自分宛ての通知一覧・詳細表示、端末通知 | ポーリング方式 |
| 6 | Androidアプリ: 「確認しました」操作 → バックエンドへ記録 | 通知ID・職員ID・確認日時 |
| 7 | PC Webアプリ: 連絡事項ごとの宛先別 確認状況（未確認/確認済み）表示 | ポーリングで自動更新 |
| 8 | 架空の職員マスタ（20名）・架空の利用者・デモ用連絡事項のシード | すべて架空データ |

## 3. 今回は実装しない機能（後続段階）

- 音声録音・書類写真のアップロード、文字起こし・OCR
- iPad共有ボード（API上は `board_summary` を返すが画面は作らない。余裕があれば簡易表示）
- FCM等のプッシュ通知基盤（アプリ内ポーリング＋ローカル通知で代替）
- 勤務シフト連動、複雑な権限管理、本格的な認証
- ローカルLLM、複数事業所連携、LINE WORKS連携、ワイズマン連携

## 4. 推奨技術構成と理由

| 層 | 採用 | 理由 |
|---|---|---|
| バックエンド | Node.js 22+ / Express / `node:sqlite`（組込SQLite） | ユーザーPCにNodeあり。ネイティブ依存ゼロでWindowsでも即起動。単一プロセスでWeb画面も配信 |
| AI | `@anthropic-ai/sdk`、Tool Useで構造化JSON出力 | 分類結果をスキーマ固定で受け取れる。`AnalyzerPort` インタフェースで将来ローカルLLMに差し替え可 |
| PC側 | バックエンドが配信する静的SPA（Vanilla JS） | ビルド工程なし、Chrome/Edgeで動作、デモが安定 |
| Android | Kotlin / Jetpack Compose / minSdk 26 / OkHttp | SDK開発の要件。ポーリング（5秒）＋NotificationManager |
| 配置 | バックエンドはユーザーのWindows PC内（LAN: `http://<PC IP>:8787`）。Android実機は同一Wi-Fi | クラウド契約不要、秘密鍵はPC内のみ。クラウド版は後続 |
| 秘密情報 | `backend/.env`（gitignore）に `ANTHROPIC_API_KEY` | Androidアプリ・公開リポジトリに鍵を置かない |

### APIキー未設定時の挙動
`ANTHROPIC_API_KEY` が無い場合はルールベースの `MockAnalyzer` にフォールバックし、画面上に「モック解析」と明示する。開発・CI・鍵なし環境での動作確認用であり、デモはClaude APIで行う。

## 5. PC・バックエンド・Android の連携方法

```
[PC ブラウザ] --HTTP/JSON--> [backend :8787] --HTTPS--> [Claude API]
      ^  (ポーリング 3秒)          |  SQLite (data/heart-relay.db)
      |                            v
[Android実機] <--HTTP/JSON ポーリング 5秒-- /api/staff/:id/deliveries
[Android実機] --POST /api/deliveries/:id/ack-->
```

- 認証は第一段階では「職員アカウント選択」（架空データのため）。ヘッダ `X-Staff-Id` を付与。
- Androidは `http://` LAN通信のため `usesCleartextTraffic` を開発用に許可（後続でHTTPS化）。

## 6. データ構造と処理フロー

### テーブル
- `staff`: id, name, role（職種: 事業所長/理学療法士/看護師/生活相談員/運転手/介護職員）, duties（当日の担当業務 JSON配列: 例 "送迎(午後)", "入浴介助"）, active
- `residents`: id, name（架空）, notes
- `messages`: id, raw_text, source（手入力/FAX/電話…）, created_by, created_at, status（analyzing/proposed/sent/failed）, analysis_json, analyzer（claude/mock）, model
- `deliveries`: id, message_id, staff_id, title, body, action_required, reason, created_at, acknowledged_at
- `ack_events`: id, delivery_id, staff_id, acked_at, client（android/web）

### 処理フロー
1. PC: `POST /api/messages {raw_text, source}` → backend は `status=analyzing` で保存し、Claude に解析依頼（職員マスタ・利用者マスタを同梱）
2. Claude（Tool Use）→ `{summary, categories[], urgency, resident_id, deadline, required_actions[], recipients:[{staff_id, reason, title, body, action_required}], board_summary, excluded_note}`
3. backend は `analysis_json` を保存し `status=proposed`。PC画面に提案を表示
4. PC: 人間が宛先・本文を確認・修正し `POST /api/messages/:id/send {recipients}` → `deliveries` 作成、`status=sent`
5. Android: `GET /api/staff/:id/deliveries` を5秒ごとに取得。新着があれば端末通知
6. Android: 「確認しました」→ `POST /api/deliveries/:id/ack` → `acknowledged_at` 記録、`ack_events` 追記
7. PC: `GET /api/messages/:id` を3秒ごとに取得し、宛先ごとの ✅/⏳ を更新

## 9. 技術的な課題と解決方針

| 課題 | 方針 |
|---|---|
| Android⇄PCの通信経路 | 同一Wi-Fi LAN。PCのファイアウォールで8787許可が必要（手順書に記載）。Androidアプリ側でサーバURLを設定画面から変更可能にする |
| クラウド環境でのAPKビルド | Android SDK cmdline-tools を導入（許可ドメイン追加済み）。GradleでdebugAPKをビルドし、ユーザーが `adb install` または端末へ転送 |
| Claude出力の揺れ | Tool Useでスキーマ強制。staff_idの妥当性をサーバ側で検証。失敗時は再試行1回→mockにフォールバックせず `failed` として表示 |
| 誤配信 | AI提案は必ず人間が承認してから配信（第一段階の原則） |
| 個人情報 | シードはすべて架空。README・UIに明記 |
| 鍵の漏洩 | `.env` gitignore、`.env.example` のみコミット。pre-commit相当のチェックは手動 |

## 10. 3分デモ動画で見せる動作

1. （15秒）背景: 「情報はあったのに届かなかった」送迎の実例
2. （30秒）PC画面: 「A様は受診のため15時までに帰宅が必要」と入力 → Claudeが分類（受診/送迎/時間変更）、送迎担当・担当介護職員に**異なる本文**を提案、関係ない職員には送らない
3. （20秒）人間が提案を確認して「送信」
4. （40秒）Android実機: 送迎担当の職員アカウントに通知が届く。詳細を見て「確認しました」をタップ
5. （20秒）PC画面: 当該職員が ✅ 確認済みに変わる。未確認の職員が一目で分かる
6. （20秒）2件目: 「B様 本日欠席」→ 宛先が変わることを見せる（人に合わせた振り分け）
7. （15秒）まとめ: ローカルLLM・音声/OCR・共有ボードへの拡張構想

## 11. 仮定と未確定事項（資料に明記がないためこの計画で仮置き）

- 配信方式は「AI提案 → 人間承認 → 配信」とした（資料では未決定）。
- 職員の「当日の担当業務」は職員マスタ内の `duties` として手動設定（シフト連動はしない）。
- 認証は職員選択のみ（架空データ前提）。
- Android通知はポーリングによるローカル通知。FCMは使わない。
- 共有ボード（iPad）は画面を作らず、APIが `board_summary` を返すまでとする。
