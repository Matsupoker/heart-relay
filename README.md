## 1. なぜHEART RELAYを作るのか

このプロジェクトの開発者は、実際に介護・医療の現場で働いています。

現場では、利用者やご家族からの苦情、職員間の行き違い、上司や組織の上層部からの指摘など、さまざまな問題が起こります。そのすべてが情報伝達だけで生じるわけではありません。しかし、長く現場で仕事をする中で、問題の少なからぬ部分に**「必要な情報が、必要な人に、必要な形で伝わっていない」**という共通点があると感じてきました。

それは必ずしも大きなシステム障害や、誰かの悪意によるものではありません。単純な仕組みの不足、伝え忘れ、確認の行き違い、小さな認識のずれ。そうした日常的なことが積み重なり、思わぬトラブルにつながります。

一方で、現場の多くの職員は、目の前の仕事に真摯に向き合い、少なからず真心を注いでいます。それでも情報が届かなかった結果として苦情や叱責を受けるのは、利用者に最も近い立場で働く職員であることが少なくありません。

現場の職員は、経営者や管理職に対して不信感を抱きがちです。しかし、経営者や管理職にも、利用者、職員、事業の継続に真摯に向き合っている人がいるはずです。誰か一方を悪者にしたいわけではありません。**互いの考えや事情が十分に伝わらないこと自体が、対立や不信を深めているのではないか。** そう考えています。

だからこそ、伝達ミスや情報の埋没を減らし、必要な情報を確実に共有できる仕組みを模索したい。そのための技術として、発展を続けるAIに可能性を感じています。

## 2. なぜ今、この仕組みが必要なのか

日本の高齢化と介護・医療現場の人手不足には、切実な危機感があります。

内閣府の「令和8年版高齢社会白書」によれば、65歳以上人口は**2043年に約3,953万人でピーク**を迎えると推計されています。ただし、65歳以上人口がその後減少しても、総人口に占める高齢者の割合は上昇を続ける見通しです。

また厚生労働省は、介護職員の必要数を**2022年度の約215万人に対し、2040年度には約272万人**と推計しています。

数字の上では将来の節目が示されていても、そこで働く立場としては、「その時まで現場が持ちこたえられるのか」という不安があります。

人手が足りない、時間が足りない、費用も限られている。だからといって、情報伝達の問題を「難しいから後回し」にし続けることはできません。

**少ない人数でも、過度な負担をかけず、低コストで、確実に情報を伝えられること。** それは単なる便利さではなく、これからの現場を支えるために必要な仕組みの一つだと考えます。

HEART RELAYは、そのような現実的な課題と、現場で働く人への思いの両方を出発点としています。

- [内閣府「令和8年版高齢社会白書」第1章 第1節](https://www8.cao.go.jp/kourei/whitepaper/w-2026/html/zenbun/s1_1_1.html)
- [厚生労働省「第9期介護保険事業計画に基づく介護職員の必要数について」](https://www.mhlw.go.jp/stf/newpage_41379.html)

## 3. HEART RELAYが目指す仕組み

介護・医療の現場には、口頭での申し送り、紙のメモ、FAX、デジタル記録、電話など、さまざまな形で情報が届きます。

HEART RELAYが目指すのは、こうした情報を一か所に集め、内容を整理し、**職種・担当業務・必要性に応じて、届ける相手と伝え方を変える**仕組みです。

- 連絡事項を集約し、AIで分類・要約する。
- 誰に伝えるべきかを、設定されたルールや担当情報をもとに判断支援する。
- 受け取る職員に必要な情報を、分かりやすい形で個別に届ける。
- 「送信した」だけで終わらせず、職員が「確認しました」と応答した履歴を記録する。
- 情報の未確認や伝達漏れを把握できるようにする。

全員に同じメッセージを一斉送信するだけでは、重要な連絡がかえって埋もれることがあります。情報を増やすのではなく、**情報が正しく届き、確認できること**を大切にします。

## 4. 第一段階の到達目標

ハッカソンでは、まず次の要素が実際につながる最小構成を目指します。

- **PC用アプリ**：連絡事項の入力と確認状況の表示。Webアプリまたはデスクトップアプリを検討。
- **バックエンド**：情報の保存と振り分け、Claude APIとの連携、通知・確認履歴の管理。
- **Claude API**：架空の連絡事項の解析、分類、受信者向け内容の整理。
- **Androidアプリ**：SDKで開発し、まずは実際のスマートフォン1台にインストール。個別の通知表示と確認操作を担当。

最小の動作は以下のとおりです。

1. PCから架空の連絡事項を入力する。
2. バックエンドがClaude APIへ解析を依頼する。
3. 内容と担当情報に基づき、架空の職員に情報を振り分ける。
4. Androidアプリで通知を受け取った職員が「確認しました」を押す。
5. 確認結果がバックエンドに記録され、PC側にも反映される。

バックエンドの配置場所（PC内またはクラウドなど）や通信方式は、検証を通して決めます。**この段階ではローカルLLMの完成を必須条件とせず、まず情報伝達の一連の流れを実証します。**

## 5. AIとローカルLLMの将来構想

将来的には、施設内の管理された環境で動作する**オンプレミスのローカルLLM**を活用し、情報を外部へ送信せずに処理できる構成を目指します。

介護・医療の情報には、慎重な取扱いが必要な内容が多く含まれます。外部サービスへの情報送信が難しい現場でも利用できるよう、ローカル処理は重要な選択肢だと考えています。

ローカルLLMの性能向上や導入費用の低下が進めば、小規模な事業所では比較的安価な機器で、大規模な介護・医療法人では相応のサーバーや管理体制で、同じ考え方を活用できる可能性があります。

ただし、**ローカルLLMを使うだけで個人情報保護や安全性が確保されるわけではありません。** アクセス制御、運用規則、データ保護、監査、責任分担などを含む設計が必要です。

## 6. 重要事項：実験的開発と個人情報の取扱い

本プロジェクトは、介護・医療現場における情報の集約・判断支援・個別伝達の可能性を検証する、ハッカソン用の**実験的プロトタイプ**です。

開発・検証ではAnthropicのClaudeなど外部AIを使用するため、利用者・職員の氏名、属性、予定、連絡事項などは**すべて架空のシミュレーション用データ**とします。**実在する利用者・職員の個人情報は使用せず、外部AIに入力せず、公開リポジトリにも掲載しません。**

将来、実際の現場で運用する際には、個人情報の利用目的、提供先での取扱い、法令、契約、施設方針を確認し、必要な承認と技術的・組織的安全対策を整える必要があります。日本の個人情報保護法が外部AIの利用を一律に禁止しているという意味ではなく、具体的な利用方法に応じた慎重な判断が必要です。

**現段階のHEART RELAYは、実在する個人情報を処理する運用を目的としていません。**

## 7. このプロジェクトが示したいこと

この仕組みがすべての問題を解決できるとは考えていません。AIの分類や振り分けにも誤りは起こり得ますし、現場に導入するには多くの課題が残ります。

それでも、情報が伝わらなかったために起こるトラブルを減らし、職員と管理者、利用者とご家族の間にある不必要な行き違いを少しでも減らせる可能性を示したいと考えています。

**人間が人間に向き合い続けるために、技術で何ができるのか。**

HEART RELAYは、その問いに対する一つの試みです。

### 画面構成（UI刷新 2026-11-07）

PC 画面は単一ページ（`web/index.html`）のままハッシュルーティングで画面を切り替えます。

- `#/home` ホーム: 本日の配信件数・未確認・確認完了と「今日の連絡」
- `#/new` 新規連絡: 入力 → AI 提案 → 承認
- `#/deliveries`、`#/deliveries/<id>` 配信管理: 一覧と詳細（職員別の確認状況、AI の選定理由）
- 共有ボード `board.html`: 新しいタブで開く
